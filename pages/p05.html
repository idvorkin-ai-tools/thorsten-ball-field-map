His agentic-coding writing, essay by essay

Twenty pieces over thirty-two months, read in order. The interesting thing is less any single claim than how far he travelled between them.
SourceThere’s Beauty in AI (Register Spill, May 2025) ↗
TL;DR — In March 2024 Thorsten used ChatGPT the way he used Google and typed the real code himself. By May 2025 an agent wrote most of what he committed, and he described his job as drawing the outline for it to fill in. A month later the agent was handing work to other agents. By August 2026 he was running many agents at once on remote machines Amp calls orbs and asking each for proof instead of reading its diff. In September 2026 he wrote that code review is already dead. Along the way he retired several of his own earlier positions in public, and those retractions are the best guide to the shift.

Read in sequence, these pieces are a lab notebook. Each one records what the tools could do that month and what he concluded from it. Several later pieces explicitly overrule earlier ones.

The arc in one picture

2024 to January 2025: a tool among tools

How I Use AI (2 March 2024). A time-stamped log of two working days at Zed plus a Saturday. He asks ChatGPT about Unix process groups at 6:30am, asks Zed’s inline assist to edit a Cargo.toml line, has it fill in test bodies for Bitbucket URL parsing and then writes the implementation himself because its version was wrong. The claim is modest: AI is useful the way a search engine is useful, sometimes very good and sometimes useless, and you can use it without holding an opinion on whether it is good for the world.

They all use it (20 November 2024). A hallway conversation with an engineer who tried “some website” once and gave up. Thorsten’s complaint is about curiosity. You can think AI is overhyped, he writes, but if the programmers you admire (he names Andreas Kling, Mitchell Hashimoto, Fabrice Bellard, John Carmack and others) are using it, refusing to even look is the strange position. This added the social argument: this was no longer about his own workflow but about what he expected from the profession.

Surely not all code’s worth it (18 December 2024). A reply to readers of the previous post who said they want to learn from writing code, or enjoy every line. He agrees that some code deserves that care, then lists three throwaway tools he had Claude write: a 50-line script that converts his newsletter archive to Markdown, a 200-line diff viewer in one HTML file, a 120-line file-sorting web app. Nobody will read that code again and its blast radius is a folder under git. Handing it off frees time for code he does care about. The new idea is a split between code that matters and code that does not, and it shows up again in every later piece.

Judging Code (22 January 2025). A tutorial in Rust: send a file and a list of constraints, some marked must-have, to Claude at temperature 0, and get back a score from 0 to 5. He points it at his own homepage and gets the same score on ten runs. The surprise for him was reliability. A model can act as a “fuzzy-to-non-fuzzy adapter”, turning a question you can state in a sentence but not easily in code (does this page show the sign-in button?) into a number. This is the first piece where the model checks work rather than produces it, which is the root of the “proof” idea he reaches in 2026.

How might AI change programming? (30 January 2025). It opens: “AI will change programming. I’m convinced of it now.” His reason is economic. Even if progress stopped that day, making a certain kind of code cheap to write and rewrite changes the field the way compilers and version control did. Then come fourteen open questions, such as whether a CONTEXT.md becomes the new robots.txt and whether code gets written for an LLM reader. The post asks rather than answers, which is why it later makes a good yardstick.

May 2025: from slot machine to agent

There’s Beauty in AI (6 May 2025). The most personal piece in the set, and the one that explains why he changed his mind. For two years he studied LLMs out of duty and felt nothing.

These LLMs are slot machines, I thought.— Thorsten Ball, There’s Beauty in AI

Two experiences at Zed changed that. Cursor’s Tab predicted his next edit and where his cursor should go, faster than his fifteen years of Vim, which made the model feel like a mechanical helper rather than an oracle. Then fine-tuning a model at Zed showed him how the training data shapes what comes out, so the output stopped looking like luck. He ends with an image of models as giant orbs of distilled human text, with each prompt a line cast into them, and an agent’s tool calls pulling that line around. It is a coincidence worth noticing that “orb” reappears fourteen months later as the name of Amp’s remote machines.

Amp is now available. Here’s how I use it. (15 May 2025, Amp note). Nine days later, Amp came off its waitlist and he wrote down his workflow after ten weeks with it. He guesses Amp writes 70 to 80 percent of the code he commits.

That’s right — I barely write code by hand anymore. If I type code, it counts.— Thorsten Ball, Amp is now available. Here’s how I use it.

His model is “paint-by-numbers”: he makes the architectural decisions and writes a prompt that carries everything he knows (relevant files, traps, constraints, which tests to run), and the agent fills it in. His habits: keep threads short because Claude Sonnet 4 gets blurry past about 100k tokens; let the agent take screenshots of a running storybook so it can see its own UI work; ask it to review its own git diff as if someone else wrote it; use git staging as the undo button. The note now carries an “Archived” banner saying it describes a much older Amp and is no longer how he works, which is the clearest sign of how quickly this advice aged. The mechanics of the agent loop itself are on page 04 (How to Build an Agent).

June to September 2025: agents that spawn agents, and code as glue

Agents for the Agent (10 June 2025, Amp note). A subagent is just another tool: the main agent writes a prompt and starts a second agent, the way a person would. Amp always had a read-only search subagent. Earlier general-purpose ones were never invoked by Claude 3.7 Sonnet, but Claude Sonnet 4 delegated eagerly, so Amp shipped generic subagents that can write files and run commands. The insight he takes from Geoff Huntley is about context. Each subagent has a fresh context window, so a messy fix that takes many attempts costs the main agent only the tokens for the prompt and the result, and several can run in parallel. That undercuts the advice from a month earlier: if delegation manages context for you, careful short threads and plan files matter less. He ends with open questions instead of a verdict.

A New Kind of Code (21 September 2025). Imagine a button that produces 500 lines of working, unclever code in a minute. Coding agents are that button. He argues that the common “it can’t write the code I write” test misses the point. For thirty years code was expensive, like bolts and screws, and tooling tried to reduce how much of it you had to write. Now there is glue, and the question is what you can build with glue. It extends “Surely not all code’s worth it” from a personal habit to a claim about what kind of material software has become.

Winter 2025–26: essays hidden in the newsletter

His weekly link roundup, Joy & Curiosity, often opens with a few paragraphs that work as a short essay. Three of them belong here.

Joy & Curiosity #68 (3 January 2026). 2025 was the year he found that typing code by hand now frustrates him, the way filling out a paper form does, because Amp is faster and better at it. He was sad until he worked out that what he loves is learning and making computers do new things, not the typing. Compare that to December 2024, when he defended the people who enjoy every line.

Joy & Curiosity #73 (8 February 2026). He quotes four of his own questions from “How might AI change programming?” and says a year later they sound naive. Documentation for agents is a given, language servers look dead, and codebases are being shaped for agent readers. His example is a debate with colleagues about UUIDs: he objected that they are ugly, then conceded that agents will read far more of them than he will.

Joy & Curiosity #80 (29 March 2026). A working theory for why agents sometimes do well and sometimes badly: what matters is where the knowledge about the task lives. If it is in the prompt, the codebase or the training data, things go fine. If it is in none of them, the agent guesses. This is the seed of his Laracon talk four months later.

June and July 2026: notes to a team that no longer types

Two posts are internal Slack messages to the Amp team, published later. Neither is about agents directly. “Building Software Is Learning” never uses the word, and “Ownership” uses it once. They belong on this page because they show where he thinks the hard part moved once code got cheap.

Building Software Is Learning (2 June 2026). When you build something new without a spec, the first version will be wrong, because writing the spec in full is what programming is. You cannot avoid the “that’s not what I meant” moment, only make it arrive sooner: a one-hour prototype, a 30-minute written plan, a faked demo video, the README example before the SDK, shipping one slice a day. The only question that matters is how soon you get feedback.

Ownership (8 July 2026). Owning a task means taking it from “we have a problem” to “we don’t have to think about it again”: question the problem, consider edge cases, failures and data, test it by hand, confirm it works in production, and tell colleagues, customers and the world. Small teams without PMs or QA need this. The one mention of agents is telling: you can ask one to run through test scenarios as part of checking your work. Execution is assumed. Judgment and follow-through are the job.

July and August 2026: orbs

Amp launched Agents in Orbs on 30 June 2026. Put plainly, an orb is a remote machine that Amp starts for one thread. It holds a checkout of your code, the agent runs on it, and you control it from the web, your phone or the CLI. It sleeps when the agent is idle and costs nothing while asleep. It wakes when you send another message. You can start as many as you like. Three notes followed, and they do different jobs.

Putting an Agent in an Orb (2 July 2026). The engineering note. Each orb runs Debian 12 with common tools preinstalled. A repo’s .agents/setup script runs when a fresh orb is made (Amp’s own is a 428-line Bash script that starts PostgreSQL tuned for speed, seeds test users and installs pinned toolchains), and .agents/resume runs on every wake-up. The rest is about making the codebase legible to an agent working on a headless remote machine: a script that puts the dev server into a known-good state whatever state it was in, a JSON file of ports, /__dev endpoints that log the agent in as any test user without OAuth, browser console output forwarded into one grep-able log, and 41 AGENTS.md files. He sums it up in four words: “don’t make them guess.”

What I Want to Tell You About Orbs (4 August 2026). The persuasion note. It opens with a long burger analogy: listing ingredients does not make anyone hungry. So instead of features he describes what changed in his own work. Because orbs remove the friction of extra checkouts, worktrees and port clashes, he starts an agent for every papercut. And because a long-running agent no longer ties up his laptop, he lets each one go further and asks for proof.

I want you to give me 100% proof that what you did works. Test this end to end.— Thorsten Ball, What I Want to Tell You About Orbs

The agents run for eight to thirty minutes and come back with screenshots, tables of cases and demo videos. That is why he says everything changed. A mountain of code you would have to read becomes a mountain of code plus evidence that it works, so review gets lighter and more ships. He calls it possibly a bigger change than coding agents themselves.

Orbs, Explained (25 August 2026). The definition note, prompted by readers annoyed at the name. Yes, an orb is a VM or sandbox. It is called something else because of what surrounds it: portals (any HTTP port opened inside Amp, annotatable and shareable by URL), a shareable thread, multiplayer orbs where teammates chat with you and the agent, review and file panels, a terminal, schedules (“do this every 45 min for the next 8 hours”), and agents that start other orbs and message each other.

The two near-identical subtitles. On the Amp notes index both orb notes carry the same line, “Everything has changed for us with orbs. How do I make you believe me?”, with a stray “to” in the August 4 version. That line fits the August 4 note, which is entirely about making you believe him. Orbs, Explained looks like it reused the subtitle: its body is a plain answer to “what is an orb?”, not an attempt at persuasion. Read August 4 for why he cares, and August 25 for what you actually get.

29 July 2026: Think Harder: How I Prompt

His Laracon US talk (video) turns the J&C #80 theory into a method. His one takeaway is a question to ask of every prompt: how is the model supposed to know what I mean? The model knows its training data and whatever is in its context window, nothing more. He uses the image of a senior engineer kidnapped, hooded and dropped at a desk with a codebase and a note telling them to fix the bug with the upload. The examples are real prompts from building Amp: a long one that points at folders, files and docs and spells out constraints; a “one-two punch” that first asks the agent to find the relevant code and then makes the request; screenshots of Slack threads standing in for typed context; auto-generated debug prompts. The end point is to move the how-to out of the prompt and into the codebase through AGENTS.md files, so “take a screenshot” is enough because the repo explains how. That is the same idea as the orb note’s paved paths. In the Q&A he explains how to keep a mental map without writing the code: know what is load-bearing, watch the agent closely when it touches those parts, write the domain rules down so it can check against them, and care less about review the closer you get to the edges.

September to November 2026: planting the flag

What I believe about the future of software development (19 September 2026). A list first posted on X, copied to his blog so the date is on record. It is his strongest position yet.

Code review will die. I mean: it’s already dead.— Thorsten Ball, What I believe about the future of software development

The other claims follow from it. Humans will review systems and how they fit together, not lines. Writing code stops being a craft, while building software (knowing which problem to solve, when to ship, how to get feedback) matters more than ever. Most bugs will be “you asked for the wrong thing” bugs. “Good code” was mostly about being cheap for humans to work with, and humans will not edit most code. The PM/design/engineering split goes away, and engineers who just pass tickets to agents stop being valuable. Access to tokens decides who can compete. Set this next to the May 2025 note, where he would not let an agent write critical code without close supervision, and the distance is clear.

Joy & Curiosity #105 (8 November 2026). His own summary of the year. The game changed three times, through three practices at Amp: moving everything into orbs; asking agents for “irrefutable proof”, which he calls the 10x change; and letting the agent run the whole development cycle, from shipping and watching rollouts to flipping feature flags and granting credits, with only database writes held back. He sets that against friends elsewhere still waiting on PR approvals and PMs.

How the position moved

Three threads run through all twenty pieces. First, who writes the code: him with a chatbot beside him (2024), the agent under his outline (May 2025), the agent and its subagents (June 2025), the agent alone while typing becomes a chore (January 2026), and many agents in orbs (August 2026). Second, how he trusts the output: reading it himself, then the agent reviewing its own diff, then a model as judge, then proof the agent gathers by running the thing, then “code review is dead”. Third, where the human effort goes: from writing lines to writing prompts, then to putting knowledge into the codebase, and finally to running a team whose job is fast feedback and full ownership. He says each time that the change surprised him, and he has twice archived or called naive what he wrote a year earlier, which is a reason to read his current predictions as provisional too.
